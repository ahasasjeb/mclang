MCLANG 26.3 LLM REFERENCE - ENGLISH KEYWORDS
===============================================================================
Plain-text reference for LLMs that write Mclang (.mcl) source for the Mclang
compiler in this repository. Target: Minecraft Java Edition 26.3, datapack
pack format 121.0.

HOW TO USE
- Sections 1-11 are normative rules. Section 14 holds copy-ready complete
  programs. Every example was compiled with the shipped compiler via
  `mclang check --deny-raw` (examples 12_macros and 13_raw are marked RAW:
  they compile normally but --deny-raw rejects them by design).
- A paired Chinese-keyword edition exists as mclang_llm_zh.txt. The two
  editions were translated with the repository tooling and compile to
  byte-identical datapacks, file for file.
- When this file is silent about a case, prefer the structured syntax over the
  raw escape hatches (`run "..."`, string-form `execute`). The compiler
  validates far more of the structured form.

===============================================================================
1 COMPILER INTERFACE
===============================================================================
Commands:
  mclang build <file.mcl|project-dir> [-o <output>] [--zip] [--description <text>] [--deny-raw]
  mclang check <file.mcl|project-dir> [--deny-raw]
  mclang lsp
  mclang help | mclang version

- `check` writes nothing and returns every independent diagnostic in one run;
  `build` runs the same checks, then writes the datapack only if all pass.
- Input is one .mcl file (single-module project) or a directory whose entry
  module is main.mcl. Imports reach the remaining modules.
- Default output is build/<name>; --zip writes build/<name>.zip. With --zip and
  -o, the -o path is the zip file.
- Directory projects may ship assets/pack.png, assets/pack.mcmeta,
  assets/overlays/<dir>/... and assets/structure/<name>.nbt; they are validated
  and copied into the pack.
- --deny-raw (strict mode) recursively rejects: `run "..."`, string-form
  `execute "..."`, string-form `return run "..."`, runtime macro calls
  `call f with(...)`, and macro functions that declare `nbt` parameters.
- Diagnostics are Chinese, carry source spans, and list actual vs expected
  values. Any error makes the exit code non-zero.
- Output is reproducible: same sources + flags produce identical bytes.

===============================================================================
2 LEXICAL GRAMMAR
===============================================================================
comments     // to end of line. There are no block comments.
string       "..." with escapes \" \\ \n \r \t; must not span a line.
raw string   """...""" may span lines, takes no escapes; used for JSON payloads.
number       Decimal integers in i32 range; decimals like 1.5, 0.25.
             NBT suffixes attach directly to digits:
               b/B byte, s/S short, i/I int, L/l long, f/F float, d/D double
             A suffix attached to digits is an NBT literal (`1s` = short); the time units`1 s`, `1 d` need the space.
identifier   Unicode letters/digits/underscore, cannot start with a digit.
             ASCII declaration names must be lowercase [a-z0-9_], at most 32
             chars, must not be a keyword or true/false, and must not be a
             Windows device name (con, nul, com1, lpt1, aux, prn, ...).
             Non-ASCII names (Chinese etc.) are legal: after semantic checking
             the compiler rewrites them to stable random 8-letter ASCII aliases,
             unique per project and collision-free. Never predict the alias.
keywords     Case sensitive. Each keyword has an English and a Chinese form and
             both are reserved; the two forms may be mixed in one file.
punctuation  ; , . .. :: = == != ! && || < <= > >= + - * / %
             += -= *= /= %= -> @ # ~ ^ ( ) { } [ ]
             A lone `:` is a lexical error; resource locations live in strings.
literals     true / false (Chinese 真 / 假) in boolean positions.

Statements end with `;`. A trailing `;` is optional after the `}` of query, item,
fn_tag and advancement blocks and after a standalone `nbt { ... }` statement.
An objective written with a block and a function body take no trailing `;`; an
explicit `;` there is a syntax error.

===============================================================================
3 PROJECTS AND MODULES
===============================================================================
- For directory input the entry module is main.mcl and must declare
  `namespace <name>;`. The namespace is one lowercase ASCII identifier shared
  by the whole project. Non-entry modules may omit it or repeat the same value.
- Module path = source path relative to the project root without extension:
  lib/math.mcl and lib/math/mod.mcl are both module `lib/math`; the entry is "".
- Top-level declarations are private by default. `export` exposes them to other
  modules; the importing module must `import` them.
    import lib::math;                        // whole module
    import lib::strings::{banner, on_fire};  // selected names
    import lib::strings::{banner as wel};    // alias
- Import paths start at the project root. `import main;` imports the entry
  module, so import cycles are allowed. Only modules reachable from main.mcl
  are compiled.
- Qualified output names: functions, JSON resources, advancements and fn_tags
  join module segments with `/` (lib/math/sum ->
  data/<ns>/function/lib/math/sum.mcfunction). Score variables, objectives,
  queries, items, storages and data_slots join with `.` (lib.state.total).
- `std::` is reserved for the built-in standard library; projects cannot
  shadow it.
- One .mcl file given directly is equivalent to a project whose only module is
  the entry module: no main.mcl and no imports needed.

===============================================================================
4 TOP-LEVEL DECLARATIONS
===============================================================================
A module contains only declarations. Statements live inside `fn` bodies.
Trailing `;` is optional after query/item/fn_tag/advancement blocks and after a
standalone nbt statement; objective blocks and function bodies take none. Plain
declarations (namespace/score/resource/storage/data_slot/...) require `;`.

4.1 namespace
    namespace <lowercase_ascii_name>;
  Exactly one namespace per project, declared by the entry module.

4.2 import / export
    import a::b;                                 whole module
    import a::b::{name, other as alias};         selected names
    export fn ...; export score ...; ...         expose a declaration
  Imported names can be used anywhere in the importing module; a local
  declaration with the same name wins. Two whole-module imports that export the
  same name is an error; use selected imports or `as`.

4.3 score - global persistent score variable
    score <name> = <i32>;
  Stored on the fake player `#v_<name>` in the compiler objective. Survives
  /reload; the generated __mcl/load only seeds values that are missing.

4.4 objective - user scoreboard objective
    objective <name>;
    objective <name> {
        criteria = "dummy";                    // or trigger, deathCount, health,
                                               // minecraft.custom:minecraft.jump,
                                               // minecraft.mined:minecraft.stone, ...
        display_name = text("Label") { ... };  // component or string
        render_type = "integer";               // integer | hearts
        number_format = blank | fixed(<component>) | styled("<json style>");
        display_slot = "sidebar";              // list|sidebar|below_name|sidebar.team.*
    }
  Runtime objective name is `<namespace>_<name>`. __mcl/load creates it and
  applies display settings; /reload never clears existing scores. statistics
  criteria are validated against the 26.3 registry.

4.5 query - reusable entity selector (no command is emitted for it)
    query <name> = entity("<entity type or #tag>") {
        tag("<tag>");                            // repeatable
        without_tag("<tag>");                    // repeatable
        without_type("<id or #tag>");            // repeatable, only after entity("#tag")
        limit(<positive int>);
        within(<non-negative int>);              // selector distance=..N
        sort(nearest|furthest|random|arbitrary);
        name("<name>"); without_name("<name>");
        scores("<objective>", "<range>");        // repeatable, merged into scores={...}
        nbt(<SNBT compound>); without_nbt(...);
        box(<x>, <y>, <z>, <dx>, <dy>, <dz>);
        distance("<range>");                     // merges with within
        level("<range>");                        // players only
        gamemode("survival|creative|adventure|spectator");   // players only
        team("<team>"); without_team("<team>");
        rotate("<yaw range>", "<pitch range>");
        predicate("<ns:id>");
        advancements("{ns:path=true/false}");
        item(<slot>) { id = "<id|#tag|predicate>"; count = <n>; custom_name = "<text>"; }
    }
  Rules: entity(...) already asserts the positive type, so type(...) is
  contradictory and rejected. tag/without_tag/without_type/scores may repeat
  (same value twice is rejected); every other property appears at most once.
  Ranges accept `a..b`, `a..`, `..b`, single numbers; inverted or negative
  distance/level bounds are errors. `limit(1)` is required wherever a single
  entity is needed (data, xp.query, teleport-follow, store.data, data_slot
  operations, item commands, ...). For `entity("#tag")`, further refinements
  are only the exclusion properties that vanilla allows.

4.6 item - reusable item stack with components
    item <name> = item_stack("<item id>") {
        count = <int, default 1>;
        custom_name = "<text>";
        item_name = "<text>";
        lore("<text>");                          // repeatable
        enchantment("<enchantment id>", <level>);        // repeatable
        stored_enchantment("<enchantment id>", <level>); // repeatable
        damage = <int>;
        max_damage = <int>;
        max_stack_size = <int>;
        rarity = common | uncommon | rare | epic;
        item_model = "<resource location>";
        dyed_color = <RGB int>;
        enchantment_glint_override = true | false;
        unbreakable = true | false;
        custom_data = nbt { ... };
        components = nbt { "minecraft:<component>" = <SNBT>; "!minecraft:<component>" = {}; };
    }
  `components` patches arbitrary 26.3 data components; a key prefixed with `!`
  removes that component. Component names are validated against the registry;
  duplicate or conflicting settings are errors. `custom_data` writes the
  minecraft:custom_data component. max_stack_size > 1 forbids max_damage.
  give counts must be 1..max_stack_size*100 (default max_stack_size is 1).

4.7 storage - item list location for self.save_items/restore_items
    storage <name> = item_list("<storage resource location>", "<NBT path>");
  __mcl/load initializes the path to an empty list if missing; /reload does not
  wipe existing contents.

4.8 data_slot - named NBT position for self.deposit/withdraw/remove_data
    data_slot <name> = item_data("<path>");      // Item.components."minecraft:custom_data".<path>
    data_slot <name> = entity_data("<path>");    // data.<path> on the entity
  Paths are dotted keys with optional [index] and quoted keys, e.g.
  pc_items, pc_note.name, records[0].payload. item_data slots may only be used
  with minecraft:item queries; entity_data slots may not target players.

4.9 resource - raw JSON resource
    resource <kind> <name> = """<json>""";
  kind is a resource directory from the 26.3 resource registry (see 10.9),
  e.g. predicate, recipe, loot_table, damage_type, "tags/block",
  "worldgen/feature". `recipe`, `predicate`, `dialog` also accept the Chinese
  words. name is an identifier or a quoted string. The JSON is parsed at
  compile time; predicate inline objects need a registered `type`; recipes and
  loot_table pools are partially schema-checked. Output path:
  data/<namespace>/<kind>/<name>.json.

4.10 advancement - the only event entry point of a datapack
    advancement <name> {
        parent = <declared advancement> | "<external id>";        // optional
        criterion <criterion name> {
            trigger = <26.3 CriteriaTriggers name>;               // may omit minecraft:
            conditions = """<trigger condition JSON>""";          // optional
        }                                                          // 1+ required
        requirements = all | any;                                  // default all
        reward {
            function = <declared fn> | "<external id>";
            experience = <int>;                                     // default 0
            loot = <declared loot_table> | "<external>";            // repeatable
            recipe = <declared recipe> | "<external>";              // repeatable
        }
        display {
            icon = <declared item>;                                 // required in display
            title = "<text>"; description = "<text>";               // required in display
            frame = task | goal | challenge;                        // default task
            background = "<texture location>";   // REQUIRED for root, FORBIDDEN for children
            show_toast = true; announce_to_chat = true; hidden = false;
        }
    }
  An advancement fires once; to make an event repeatable call
  `advancement.revoke(self, <advancement>)` inside its reward function.
  requirements=all emits one single-name group per criterion (AND);
  requirements=any emits one group with all names (OR).
  conditions keeps the vanilla JSON; known trigger condition fields are checked
  against the 26.3 snapshot. An inline condition `type` must be a registered
  26.3 loot condition (the `minecraft:` prefix is optional, near misses get a
  suggestion); `all_of`/`any_of` `terms` and `inverted` `term` are checked
  recursively, and `listOf()` fields (`victims`, `items`, `ingredients`) only
  accept arrays. 26.3 inline loot conditions use `type` as the
  discriminator, e.g. block match:
    {"location":{"type":"minecraft:match_block","blocks":"minecraft:dirt"}}
  and entity predicates are nested:
    {"entity":{"type":"minecraft:entity_properties","entity":"this",
               "predicate":{"minecraft:entity_type":"minecraft:zombie"}}}

4.11 fn_tag - function tag
    fn_tag <name> {
        value(<declared function>);
        value(#<declared tag>);
        value("<external function id>");
        value("#<external tag id>");
        replace = true | false;                 // default false
    }
  Written to data/<namespace>/tags/function/<name>.json. Local references are
  checked for existence and cycles. `call #tag()` expands all members and
  checks their parameter/context requirements.

4.12 fn - functions
    [@load|@tick|@entity|@player|@non_player] fn <name>(<param>, ...) [-> score] { ... }
    [@same attributes] macro fn <name>(<type> <macroparam>, ...) { ... }
  Attributes (mutually exclusive groups):
    @load   runs on load and /reload. No parameters, no return value.
    @tick   runs every game tick. No parameters, no return value.
    @entity         requires any entity context.
    @non_player     requires a definite non-player entity context.
    @player         requires a player context.
    @load/@tick cannot combine with the entity attributes.
  Ordinary parameters are stored in private fake players `#p_<hash>`; the
  caller writes them before `function <ns>:<fn>`. Therefore a parameterized
  function called directly by Minecraft (or by `schedule`) sees stale values;
  such calls are rejected at compile time. Parameter names must not collide
  with global score variables (they always exist).
  A `-> score` function must end with an explicit `return`.
  macro fn types: integer, decimal, text, resource, nbt. Text/NBT strings may
  contain `$(name)` placeholders; coordinates may be `macro(name)`. Macro
  parameters are not score variables and cannot mix with ordinary parameters.
  Macro functions cannot be @load/@tick and cannot return a value.

===============================================================================
5 STATEMENTS
===============================================================================
Every statement ends with `;` unless it ends with a `}` block.

5.1 ASSIGNMENT AND let
    let <name> = <expr>;          // lexical local, block scoped
    <name> = <expr>;              // score variable (global) or local
    <name> += <expr>;  -=  *=  /=  %=
  Locals may not shadow global score variables or parameters. Division or
  modulo by a constant 0 is a compile error. Locals live in `#l_<hash>` slots.

5.2 CONTROL FLOW
    if <condition> { ... } else { ... }
    while <condition> { ... }
    for <name> in <start>..<end> { ... }
    break;      continue;
  - Conditions that are constant at compile time are folded: `if 1 == 1`
    inlines the then-branch, `if 2 < 1` disappears, `while 0 == 1` emits nothing.
  - Consecutive nested `if` statements merge into ONE vanilla condition chain
    (`execute if ... if ...`), and a condition already implied by the chain is
    not tested twice (`if a && a`, `if x > 10 { if x > 5 { ... } }`); a
    contradictory chain (`if x > 10 { if x < 5 { ... } }`) emits nothing.
    Conditions with side effects (function/predicate) keep the original path.
  - `&&` and `||` short-circuit left to right; the left side is always
    evaluated exactly as written, and a provably true right side never removes
    the left call. When the right side of `&&` is a comparison it gets no
    separate flag score.
  - Comparison ranges render exactly like vanilla: `x < c` is `matches ..c-1`,
    `x > c` is `matches c+1..`, `x == c` is `matches c`, `x != c` is
    `unless ... matches c`; literals always stay inside i32, so impossible
    comparisons (`x < -2147483648`, `x > 2147483647`) emit no test at all.
  - `for` is half-open [start, end); the end expression is evaluated once
    (dynamic ends are stored in a temp slot). An empty constant range emits
    nothing. break/continue only work inside the innermost for/while; they are
    rejected in each/spawn.
  - `return` may appear ONLY directly in the outermost function body. Blocks
    (if/while/for/each/spawn/execute/in_dimension) lower to helper functions,
    so a return inside them would only end the helper. Assign a local and
    return at the end instead.

5.3 ENTITY BLOCKS
    each(<query>) { ... }
      Executes the body once per matching entity with @s set; player queries
      give player context, other queries give non-player entity context.
    spawn("<entity type>"[, <pos|vec3>]) { ... }
      Summons at the current position (or the given one); body runs with the
      new entity, always non-player. minecraft:player and
      minecraft:fishing_bobber cannot be summoned.
    in_dimension("<dimension id>") { ... }
      Runs the body in that dimension; execution entity is unchanged.

5.4 STRUCTURED execute
    execute [<modifiers>...] [if <condition> | unless <condition>]... [<stores>...] { ... }
  Clause order is fixed: modifiers, then conditions, then stores. Repeated
  modifiers or conditions/stores written before modifiers are errors.
  Modifiers:
    as(<query>)             run as each matched entity (changes @s)
    at(<query>)             run at each matched entity (keeps @s)
    positioned(<pos|vec3>)  set position, reset anchor to feet
    rotated(rotation(yaw, pitch))
    facing(pos(<x>,<y>,<z>)) | facing(entity(<query>), eyes|feet)
    align(x|y|z subset, e.g. xz)   align execution position to blocks
    anchored(eyes|feet)
    in("<dimension>")
    on(<relation>)          relation: owner|leasher|target|attacker|vehicle|
                            controller|origin|passengers
    summon("<entity type>") summon and continue as the new entity
  Conditions reuse the whole condition language (section 6) and short-circuit
  left to right. Stores capture the last command of the body:
    store.result(<holder>, <objective>)       command result (int)
    store.success(<holder>, <objective>)      1 on success, else 0
    store.result(bossbar, "<id>", value|max)
    store.success(bossbar, "<id>", value|max)
    store.data([result|success,] <source>, "<path>", byte|short|int|long|float|double[, scale])
      <source> is entity,<holder> | block,<pos> | storage,"<id>"
  Store rules:
  - The body's last statement MUST be a plain command/assignment/scoreboard
    set or a call to a `-> score` function. Ending with if/while/each/spawn/
    execute is rejected.
  - If conditions do not hold, the body never runs and nothing is stored.
  - `<holder>` accepts self, origin or a query (query selector may write many
    entities). origin is captured to a temp and copied with `on origin`, so a
    miss leaves the target unchanged.
  - store.data entity sources require limit(1); self requires non-player.

5.5 CALLS AND SCHEDULING
    call <fn>(<args>...);     |  <fn>(<args>...);      // shorthand
    call #<fn_tag>();         |  call "<external:fn>"();
    let <name> = <fn>(<args>...);        // only for -> score functions
    schedule <fn>() after <number> t|s|d [append|replace];
    schedule #<fn_tag>() after <number> t|s|d [append|replace];
    schedule.clear(<fn>);
  Arguments are evaluated left to right into parameter slots, then
  `function <ns>:<name>` runs. Argument count, parameter types and context
  requirements are checked. Tags take no arguments, so every member of a
  called tag must also be parameter-free. `schedule` runs in a future tick
  with no entity context, so the target function must have no parameters and
  no context attribute; default mode is replace. schedule.clear accepts a
  function only (not a tag). Times round like vanilla: 20 t = 1 s, 24000 t = 1 d.

5.6 give AND self ACTIONS
    give(<player query>|self, <item>[, <count>]);
    give(origin, <item>[, <count>]);
    give(<player query>|origin|self, self.item);
    self.add_tag("<tag>");
    self.remove_tag("<tag>");
    self.remove();
    self.set_invulnerable(true|false);
    self.set_no_gravity(true|false);
    self.save_items(<storage>);
    self.restore_items(<storage>);
    self.remove_preserving_items(<storage>);
    self.remove_preserving_items(<data_slot>, <limit(1) query>);
    self.deposit(<data_slot>, <limit(1) query>);
    self.withdraw(<data_slot>, <limit(1) query>);
    self.remove_data(<data_slot>);
    self.give_item(<item>[, <count>]);
    self.clear_items();
  Context requirements: add_tag/remove_tag/remove need entity; set_*,
  save/restore/remove_preserving, clear_items, deposit/withdraw/remove_data
  need a definite non-player entity (they write NBT); give_item needs player.
  `give(x, self.item)` hands the current entity's item (slot 0) to the target
  player and only clears the source slot when the copy succeeds.
  deposit appends @s.Items into the queried entity's slot; withdraw loads and
  deletes the source slot. remove_preserving_items(slot, q) appends first and
  kills @s only when the container is empty, so items are never dropped.

5.7 MESSAGES AND SOUND
    message.all(<component>|"<text>"[, <color>]);
    message.self(<component>|"<text>"[, <color>]);          // player context
    message.nearest(<1..30000000>, <component>|"<text>"[, <color>]);
    message.player(<player query>, <component>|"<text>"[, <color>]);
    sound.self("<sound id>", <sound category>);              // player context
    sound.play("<sound id>", <sound category>, <player query>
               [, <pos|vec3>][, <volume>][, <pitch 0..2>][, <min volume 0..1>]);
  Optional arguments fill vanilla order; category values: master, music,
  record, weather, block, hostile, neutral, player, ambient, voice, ui.
  A trailing color word after a plain string is classic shorthand; structured
  components use the style block instead.

5.8 TEXT COMPONENTS AND UI COMMANDS
    text("<text>") { <style> }
    translate("<key>"[, [<component>, ...]]) { <style> }
    keybind("<key>") { <style> }
    object(atlas, "<sprite>"); object(player, "<name>"[, <hat>]) { fallback = <component|string>; }
    score(<holder>, <declared objective> | "<runtime objective>") { <style> }
    selector("<selector>" | <query>) { <style> }
    nbt(entity, <holder>, "<path>") { <style> }
    nbt(block, <pos>, "<path>") { <style> }
    nbt(storage, "<id>", "<path>") { <style> }
  Style keys (each at most once): color (16 color names or "#rrggbb"),
  bold, italic, underlined, strikethrough, obfuscated (true/false),
  click = open_url("...")|run_command("/...")|suggest_command("/...")|
          copy_to_clipboard("...")|change_page(1..2147483647)|
          show_dialog("<dialog id>")|custom("<event id>"[, nbt {...}]),
  hover = <component>|show_item("<item id>"[, count])|show_entity("<type>","<uuid>"[, name]),
  fallback (object only), interpret/plain/separator (nbt component only).
  Colors: black dark_blue dark_green dark_aqua dark_red dark_purple gold gray
  dark_gray blue green aqua red light_purple yellow white (Chinese names too).

    title.title(<player target>, <component|string>);
    title.subtitle(...); title.actionbar(...);
    title.times(<target>, <fade in>, <stay>, <fade out>);
    title.clear(<target>); title.reset(<target>);
    bossbar.add("<id>", <component|string>);
    bossbar.remove("<id>"); bossbar.list();
    bossbar.set.name("<id>", <component|string>);
    bossbar.set.color("<id>", pink|blue|red|green|yellow|purple|white);
    bossbar.set.style("<id>", progress|notched_6|notched_10|notched_12|notched_20);
    bossbar.set.value("<id>", <non-negative int>);
    bossbar.set.max("<id>", <positive int>);
    bossbar.set.visible("<id>", true|false);
    bossbar.set.players("<id>"[, <player target>]);        // no target = clear list
    let <name> = bossbar.get("<id>", value|max|visible|players);
    dialog.show(<player target>, <declared dialog> | "<external dialog id>");
    dialog.clear(<player target>);
    particle("<particle id>"[, nbt { <options> }][, <pos|vec3>
             [, vec3(<dx>,<dy>,<dz>), <speed>, <count>
             [, normal|force[, <player target>]]]]);
    stopsound(<player target>[, <category>|*[, "<sound id>"]]);
    posteffect.add(<player target>, "<post effect id>");
    posteffect.clear(<player target>);
    posteffect.list(<limit(1) player query>);
    posteffect.remove(<player target>, "<post effect id>");
    msg(<player target>, "<single line>");
    teammsg("<single line>");                                  // entity context
  A "player target" is a player query, `self` (player context) or `origin`
  inside `execute on(origin)` blocks. Particle types are vanilla 26.3 ids;
  options are checked against the particle codec. say(...) and me(...) are
  native broadcasts with the MessageArgument rules (single line, <= 256 UTF-16
  units, selectors without [...] only).

5.9 EFFECT, XP, clear, STOPWATCH
    effect.give(<query>, "<effect id>", <seconds 1..1000000>[, <amplifier 0..255>][, <hide particles>]);
    effect.give_infinite(<query>, "<effect id>"[, <amplifier>][, <hide particles>]);
    effect.clear(<query>[, "<effect id>"]);
    xp.add(<player query>, points|levels, <int>);              // negative allowed
    xp.set(<player query>, points|levels, <non-negative int>);
    let <name> = xp.query(<limit(1) player query>, points|levels);
    clear();
    clear(<player query>);

6 EXPRESSIONS AND CONDITIONS
===============================================================================
6.1 EXPRESSIONS (all yield a 32-bit score value)
    <int>                                   i32 constant, folded at compile time
    <name>                                  global score, parameter or local
    <fn>(<args>...)                         call of a -> score function
    scoreboard.get(<holder>, <objective>)
    xp.query(<limit(1) player query>, points|levels)
    stopwatch.query("<id>"[, <scale>])
    time.query(["<world clock>"]); time.query_gametime()
    gamerule.query("<rule>"); worldborder.get(); difficulty()
    bossbar.get("<id>", value|max|visible|players)
    count(<query>)                          number of matching entities
    random(<min>, <max>)                    inclusive random int (no sequence)
    data.get(<source>, "<path>"[, <scale>])
    compute(<default|block,<pos>|entity,<holder>>, float|integer, "<provider>"[, <scale>])
    <integer-returning extended command>    e.g. tag.list(...), attribute.get(...)
  Operators: unary `-`; binary `+ - * / %`; parentheses. `* / %` bind tighter
  than `+ -`; equal precedence is left-associative. Pure constant expressions
  are folded; `/0` or i32 overflow in constants is an error. Runtime arithmetic
  follows vanilla scoreboard i32 semantics with floorDiv/floorMod:
  -3 / 2 == -2, -3 % 2 == 1, 3 % -2 == -1.

6.2 CONDITIONS
    <expr> == <expr>    !=    <    <=    >    >=
    !<condition>   <condition> && <condition>   <condition> || <condition>
    ( <condition> )
    predicate(<declared predicate resource>)
    block(<block pos>, <block state or #tag>)
    blocks(<from>, <to>, <destination>[, all|masked])
    biome(<block pos>, "<biome or #tag>")
    loaded(<block pos>)
    dimension("<dimension id>")
    entity(<query>)                          true when the query matches
    data(entity, <holder>|block, <pos>|storage, "<id>", "<path>")
    items(entity, <holder>|block, <pos>, "<slot>", <item predicate>)
    slots(entity, <holder>|block, <pos>, "<slot>")
    function(<declared fn or #tag>)
    stopwatch("<id>")
  Item predicate argument syntax:
    "<item id>" | "#<item tag>" | item_predicate("*"|"<id>"|"#<tag>") {
        has("<component>");
        !has("<component>") || equals("<component>", <SNBT>);
        matches("<component>", nbt { ... });            // component sub-predicate
        matches("minecraft:count", nbt { min = 1; max = 64; });
    }
  Clauses separated by `;` are ANDed; `||` inside a clause is an OR of
  alternatives; `!` negates one test. `minecraft:count` is the vanilla
  pseudo-component for stack counts.
  Evaluation: `&&`/`||` short-circuit left to right. Conditions run in the
  current execution context. Failures of entity/block/item/data lookups make
  the atom false (index misses read 0 for expressions), and negation preserves
  that boundary: `!data(entity, q, "Health")` is true when q matches nothing.
  A score compared with a constant renders a vanilla `matches` range (closed
  bounds): `x < c` is `..c-1`, `x > c` is `c+1..`, `x == c` is `c`, `x != c` is
  `unless ... matches c`; literals always stay inside i32 and an impossible
  comparison emits no test.

===============================================================================
7 EXECUTION CONTEXT
===============================================================================
Context lattice (capabilities are not inherited downward):
    none (@load / @tick)
      entity (@entity)
        mob  (@non_player, non-player each/spawn)
        player (@player, player each, player context)
  none   : no @s. Only context-free commands.
  entity : any entity, possibly a player.
  mob    : definitely not a player; required for entity-NBT writes
           (data.*, nbt merge, self.set_*, save/restore/deposit/withdraw,
           remove_data, clear_items, store.data with self).
  player : definitely a player; required for message.self, self.give_item,
           xp.*, clear()/give(self,...), title/bossbar/dialog targets when
           using self, and trigger.
  Player data is read-only for datapacks; any write to player NBT is rejected
  by Minecraft and by the compiler.
Context sources: function attribute; each(query) (player query -> player,
other -> mob); spawn body (mob); execute as/at/on/summon per vanilla rules.
at/positioned/rotated/facing/in_dimension do not change @s.

===============================================================================
8 STANDARD LIBRARY
===============================================================================
Import explicitly: `import std::math::{abs};` etc. Modules are compiled only
when reachable; importing a module emits all of its public functions. std:: is
reserved. All values are 32-bit scores; boolean helpers return 0 or 1
(0 = false, anything else = true). Time helpers use 20 ticks/second.
  std::math   abs(x), min(a,b), max(a,b), clamp(x,lo,hi), sign(x)
  std::state  normalize(x), toggle(x), latch(previous, signal),
              rising_edge(previous, current), falling_edge(previous, current)
  std::time   seconds_to_ticks(s), ticks_to_seconds(t),
              interval_due(now_tick, last_tick, period),
              cooldown_ready(now_tick, deadline_tick),
              remaining(now_tick, deadline_tick)
  std::random chance(0..100), chance_per_mille(0..1000)
  interval_due needs a strictly positive period; the caller updates last_tick on
  fire. cooldown_ready is true on and after the deadline; remaining returns the
  ticks left and 0 after the deadline. chance values outside 0..100 clamp to the
  nearest certain outcome. rising_edge/falling_edge need the caller to store the
  previous value. clamp returns the lower bound when lo > hi.

9 GENERATED DATAPACK (ABI)
===============================================================================
Layout:
  build/<name>/pack.mcmeta                     min_format/max_format = [121, 0]
  build/<name>/.mclang-manifest                rebuild bookkeeping
  data/minecraft/tags/function/load.json       -> ["<ns>:__mcl/load"]
  data/minecraft/tags/function/tick.json       @tick functions in source order
  data/<ns>/function/**.mcfunction             user functions (module path)
  data/<ns>/function/__mcl/**.mcfunction       helpers and __mcl/load
  data/<ns>/<kind>/**.json                     resources, advancements, tags
Compiler-internal names:
  mcl_<hash>          compiler objective per namespace
  #v_<name>           fake player for a global score variable
  #p_<hash>           function parameter slots (stable per parameter)
  #l_<hash>           local variable slots
  #t<n>               temporaries for expressions and conditions
  __mcl/<fn>/<n>      helper functions expanded from blocks
  __mcl/empty_slot    slot_source used by give(x, self.item)
Behavior:
- Every .mcfunction starts with `# Generated by mclang.`
- __mcl/load creates objectives, seeds only missing score variables, initializes
  item_list storages, then calls all @load functions in source order.
- Output is byte-reproducible; the Chinese and English keyword editions produce
  identical files.
- /reload does not reset scores, storages or stopwatches.

11 HARD RULES AND PITFALLS
===============================================================================
Repeat these until they are automatic; each one is enforced by the compiler.
 1. `return` is only legal directly in the outermost body of a function.
    It cannot appear inside if/while/for/each/spawn/in_dimension/execute.
    For conditional results assign a local and return at the end.
 2. A parameterized function may only be called from Mclang code: ordinary
    calls in statements/expressions or a literal macro call. It cannot be
    scheduled or invoked by vanilla /function, because parameters live in
    shared fake players that the caller must write first.
 3. `schedule` targets must be parameter-free and context-free; tags are
    allowed as targets, and every member must satisfy the same rule.
    schedule.clear takes a function only.
 4. Every single-entity parameter requires a query with `limit(1)`; the
    compiler never picks "the first" entity silently.
 5. data/NBT writes require a definite non-player context. Player NBT is
    read-only.
 6. message.self, self.give_item, xp.*, clear()/give(self,...), trigger need a
    definite player context.
 7. An `execute` store whose body ends with a control structure is rejected;
    the captured value would not be well defined.
 8. `--deny-raw` rejects run "..." / execute "..." / return run "..." /
    runtime `with` macro calls / `nbt` macro parameters. Prefer structured
    forms so strict mode stays clean.
 9. Declaration names must not be keywords (either language) or true/false,
    and ASCII names must be lowercase, <= 32 chars, no Windows device names.
10. Chinese (non-ASCII) declaration names are rewritten to stable random
    ASCII aliases. Their diagnostics keep the source name. Do not write code
    that depends on the generated alias.
11. The whole project shares one namespace; every module must either omit
    `namespace` or repeat the same value.
12. Constant folding never removes side effects: `side_effect() == 1 && 0 == 1`
    still calls side_effect() once, and if/else evaluates its condition once.
13. `for` is half-open and evaluates the end once. `while` re-evaluates the
    condition every iteration and can exhaust Minecraft's command-chain limit;
    make sure the body changes the condition or contains `break`.
14. break/continue escape only the innermost for/while. They are rejected in
    each/spawn blocks (each entity runs its own helper function).
15. /reload never resets scoreboard, storage or stopwatch data. Guard one-time
    creation with a score flag.
16. Expression queries that fail read 0; conditions that fail are false.
    `!condition` of a failed lookup is true.
17. give counts are 1..max_stack_size*100; item.replace/fill/override counts
    are 1..99. Item definitions default to count 1 / max_stack_size 1.
18. A `-> score` function must end in `return`; a void function may use bare
    `return;`. `return fail` does not produce a value.
19. `nbt { ... }` merges into @s. For block entity data use the nbt argument of
    set_block/fill. custom_data keys are user data and never aliased.
20. Generated function lines may not exceed 2,000,000 UTF-16 units; avoid
    gigantic constant fills.
21. Message arguments (say/me/msg/teammsg) are single-line strings of at most
    256 UTF-16 units; selectors with `[...]` are rejected there.
22. Text component `interpret` and `plain` cannot both be true; `fallback` only
    works on object components; interpret/plain/separator only on nbt
    components.
23. Advancement display rules: a root advancement needs `background`, a child
    with `parent` must not declare `background`; icon must be a declared item.
24. An advancement fires once; revoke it in its reward function for repeatable
    events.
25. resource JSON is parsed and partially schema-checked, but Minecraft still
    validates full codecs at load time. Only `predicate` declarations can be
    referenced from conditions.
26. `max_minecart_speed` is rejected (experimental feature not enabled by
    default).
27. name/value pairs are validated against 26.3 snapshots; do not guess
    registry names, block state properties or entity NBT keys from memory.
28. Chunk/data access at the wrong moment is not statically checkable: loaded(),
    queries and data reads can legitimately fail at runtime. Design for 0/false.

--- 01_hello.mcl: minimal complete program, @load/@tick, score, query, each ---
namespace hello;

score ticks = 0;
query all_players = entity("minecraft:player") {}

@load
fn load() {
    message.all("Hello from Mclang", green);
}

@tick
fn tick() {
    ticks += 1;
    if ticks >= 100 {
        each(all_players) {
            message.self("Five seconds passed.", gold);
            sound.self("minecraft:block.note_block.pling", master);
        }
        ticks = 0;
    }
}

--- 02_core.mcl: declarations, control flow, functions, returns, schedule, tags ---
namespace core_demo;

score counter = 0;
score total = 0;
score active = 1;

@load
fn load() {
    message.all("core demo loaded", green);
}

@tick
fn tick() {
    counter += 1;
    if counter >= 20 {
        counter = 0;
        total = compute_sum(10);
        if total > 100 {
            call #batch();
        }
    }
}

fn compute_sum(bound) -> score {
    let result = 0;
    for index in 1..bound {
        if index % 2 == 0 {
            continue;
        }
        if index >= 8 {
            break;
        }
        result += index;
    }
    while active < 3 {
        active += 1;
    }
    if result > 10 && active == 3 {
        result -= 1;
    } else {
        result += 1;
    }
    return result;
}

fn reset() {
    counter = 0;
    total = 0;
    active = 1;
}

fn later() {
    schedule later() after 1.5 s append;
}

fn cleanup() {}

fn queue() {
    schedule cleanup() after 2 d replace;
    schedule.clear(cleanup);
}

fn_tag batch {
    value(reset);
    value(#announcement);
}

fn_tag announcement {
    value(cleanup);
}
