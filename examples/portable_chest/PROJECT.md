# 便携箱子矿车测试项目

这个项目面向 Minecraft Java Edition 26.3，用来验证 Mclang 能否编译一个带**按玩家保存状态**、实体绑定、跨维度传送和多文件函数调用的实际数据包。

项目源码不包含 `run` 或字符串形式的 `execute`。实体选择器、物品组件谓词、维度切换、传送命令和文本组件 JSON 都由编译器根据类型化语句生成。

## 玩法

1. 用铁砧把一个绿宝石命名为大写单字母 `A`。
2. 丢出这个绿宝石：数据包会为投掷者分配一个独有的箱子编号，并在落点召唤一辆属于该玩家的箱子矿车；绿宝石原样回到投掷者背包。
3. 打开矿车放入任意物品。
4. 再丢一次绿宝石：数据包只收起**编号与投掷者一致**的已放出矿车——把它传送到世界边界角落的仓库里，物品从头到尾都留在矿车中。
5. 第三次触发会把仓库里的矿车传送回绿宝石的落点，物品原样还在。

多名玩家可以同时使用：每人的编号、开关状态互不影响，彼此只能收起自己的箱子。名称匹配区分大小写，也要求物品组件的值精确等于纯文本 `A`；未命名绿宝石、小写 `a`、名称 `AA` 和数量大于一的掉落堆都不会触发。

## 构建与安装

在 Mclang 仓库根目录执行：

```powershell
target/release/mclang.exe check examples/portable_chest --deny-raw
target/release/mclang.exe build examples/portable_chest --deny-raw
```

默认产物位于 `build/portable_chest`。把这个目录复制到目标世界的 `datapacks` 目录，进入世界后执行 `/reload`。也可以直接把输出目录指向世界：

```powershell
target/release/mclang.exe build examples/portable_chest -o "C:/path/to/world/datapacks/portable_chest" --deny-raw
```

## 实现要点

| 语言能力 | 在这个项目里的用途 |
| --- | --- |
| `objective` / `目标` | `box_key` 记录每位玩家的箱子编号，`box_active` 记录放出状态；玩家分数随玩家保存 |
| `scoreboard.set/reset/get` / `计分板.设置/重置/取` | 分配编号、切换状态、读取投掷者与矿车的编号 |
| `teleport` / `传送` | 收起时把矿车送进仓库坐标，放出时把矿车传送到触发物身边 |
| `in_dimension` / `在维度` | 逐个维度查找已放出的矿车；入库存放固定从主世界执行 |
| `each` + 实体计分 | 遍历已放出/仓库中的矿车，按 `box_key` 计分筛出属于自己的那一辆 |
| `self.set_invulnerable` / `自身.设置无敌`、`self.set_no_gravity` / `自身.设置无视重力` | 矿车不会被外部伤害摧毁，也不会下落或顺坡滑动 |
| `forceload`、`fill`、`set_block` | `@load` 里强制加载仓库区块并搭出屏障盒 |
| `give(origin, self.item)` | 触发用的绿宝石原样交还投掷者 |

**仓库设计**：收起时不销毁矿车、也不把物品复制到任何 NBT 里，而是把整辆矿车传送到 `(29999970, -60, 29999970)`——世界边界角落的一个屏障盒：5×5×5 的外壳，里面是 3×3×3 空气。屏障在生存模式无法破坏，坐标又远在世界边缘，正常游戏不可能到达；`forceload` 让这个区块常驻加载，选择器才能随时找到里面的矿车。收起的查找会依次扫描主世界、下界和末地（矿车可能被留在任何维度），传送的目标坐标固定包在主世界；放出时按 `pc_stowed` 标签筛出仓库中的矿车，随触发绿宝石的位置、维度一起取回。

这条路线没有数据编解码：物品从未离开矿车的 `Items`，因此不存在保存/恢复失败、掉落或复制的可能。

## 状态和边界

- **每位玩家一个箱子**：编号由全局计数器分配，只增不减；`box_key` 为 0 表示尚未分配。矿车实体上的 `box_key` 计分标识归属，`pc_box` 标签标识全部矿车，`pc_stowed` 标识收在仓库里的矿车。
- **无投掷者的触发物被忽略**：发射器、狐狸等丢出的命名绿宝石没有 `Thrower`，读取编号得到 0，源码直接跳过，不会建立共享的 0 号箱子。
- **掉落物只有一次触发**：掉落物被标记 `pc_processed`，同一枚掉落物不会每刻重复切换。
- **未加载区块中的矿车**：矿车留在远处时选择器看不到它。收起会提示「没有找到你的箱子」并保持放出状态，不会误建新箱子；放出时的仓库矿车来自常驻加载的仓库，不受影响。
- **仓库的维护**：仓库区块被 `forceload` 常驻加载。管理员执行 `forceload remove all` 会让仓库矿车不可见（靠近 30 万格外围后才会重新加载），此时再次触发会提示找不到箱子。
- **外部修改**：管理员直接删除矿车、清除计分板或破坏仓库属于外部状态修改，不在切换协议内。绿宝石丢失或删除时，矿车仍收在仓库里（编号还在玩家计分上），重新准备一枚同名绿宝石即可找回。
- 矿车可以在主世界、下界和末地之间收取；仓库固定在主世界。

## 手工验收

- 两名玩家各自触发：触发后各自只有一辆属于自己的 `pc_box` 矿车，编号计分不同。
- 玩家 A 收起箱子时，玩家 B 的箱子不受影响。
- 首次触发后只有一辆带 `pc_box` 标签的箱子矿车，触发用的绿宝石立即回到投掷者背包且名称与组件不变。
- 反复投掷同一枚绿宝石可以持续切换；不会消耗或复制绿宝石。
- 背包已满时触发，绿宝石留在投掷者附近的地面而不是消失。
- 箱内物品包含不同槽位、堆叠数、耐久和组件时，收起后地面没有掉落物（矿车整辆入库），仓库坐标处能用 `/data get entity @e[tag=pc_stowed,limit=1] Items` 看到完整列表。
- 再次放出后，物品的槽位、数量和组件保持不变。
- 在下界丢失钥匙再放出：矿车会从主世界仓库传送到下界的落点。
- 连续执行 `/reload` 后，仓库区块、已放出的矿车、已收起的矿车和每位玩家的编号都不会被重置。
- 用发射器丢出命名绿宝石不会建立箱子。
- 普通绿宝石、名称 `a`、名称 `AA` 和两个一组的 `A` 绿宝石不会触发。
