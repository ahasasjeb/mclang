# 便携箱子矿车测试项目

这个项目面向 Minecraft Java Edition 26.3-rc-2，用来验证 Mclang 能否编译一个带**按玩家保存状态**、实体绑定、物品数据寄存和多文件函数调用的实际数据包。

项目源码不包含 `run` 或字符串形式的 `execute`。实体选择器、物品组件谓词、维度切换、NBT 数据和文本组件 JSON 都由编译器根据类型化语句生成。

## 玩法

1. 用铁砧把一个绿宝石命名为大写单字母 `A`。
2. 丢出这个绿宝石：数据包会为投掷者分配一个独有的箱子编号，并在落点召唤一辆属于该玩家的箱子矿车；绿宝石原样回到投掷者背包。
3. 打开矿车放入任意物品。
4. 再丢一次绿宝石：数据包只收起**编号与投掷者一致**的矿车，把箱内物品完整寄存在这枚绿宝石自带的 `minecraft:custom_data` 里，然后移除矿车。
5. 第三次触发会重新召唤矿车，并把绿宝石里寄存的物品恢复到原槽位。

多名玩家可以同时使用：每人的编号、开关状态互不影响，彼此只能收起自己的箱子。名称匹配区分大小写，也要求物品组件的值精确等于纯文本 `A`；未命名绿宝石、小写 `a`、名称 `AA` 和数量大于一的掉落堆都不会触发。

## 构建与安装

在 Mclang 仓库根目录执行：

```powershell
target/release/mclang.exe check examples/portable_chest --deny-raw
target/release/mclang.exe build examples/portable_chest --deny-raw
```

默认产物位于 `build/portable_chest`。把这个目录复制到目标世界的 `datapacks` 目录，进入世界后执行 `/reload`。也可以直接把输出目录指向世界：

```powershell
target/release/mclang.exe build examples/portable_chest -o "C:/path/to/world/datapacks/portable_chest" --deny-raw
```

## 实现要点

| 语言能力 | 在这个项目里的用途 |
| --- | --- |
| `objective` / `目标` | `box_key` 记录每位玩家的箱子编号，`box_active` 记录放出状态；玩家分数随玩家保存 |
| `scoreboard.set/reset/get` / `计分板.设置/重置/取` | 分配编号、切换状态、读取投掷者与矿车的编号 |
| `data_slot` / `数据槽` + `self.deposit/withdraw` / `自身.存入/取出` | 在矿车 `Items` 与绿宝石的 `minecraft:custom_data` 之间搬运完整物品列表 |
| `self.remove_preserving_items` / `自身.保存并移除` | 收起矿车：追加成功才清空 `Items`、容器为空才移除，避免 `kill` 掉落物品 |
| `self.set_invulnerable` / `自身.设置无敌`、`self.set_no_gravity` / `自身.设置无视重力` | 矿车不会被外部伤害摧毁，也不会下落或顺坡滑动 |
| `each` + 实体计分 | 遍历全部 `pc_box` 矿车，按 `box_key` 计分筛出属于当前投掷者的那一辆 |
| `give(origin, self.item)` | 触发用的绿宝石原样交还投掷者 |

收起的物品寄存在绿宝石自己的 `custom_data` 里，因此物品跟着钥匙物品走：箱子不会互相串号，也不需要按玩家拆分的命令存储路径。`自身.存入` 使用追加语义，同一枚绿宝石被反复触发时不会覆盖已有寄存；收起流程使用带成功校验的 `自身.保存并移除`，只有物品确实写进绿宝石才移除矿车。

## 状态和边界

- **每位玩家一个箱子**：编号由全局计数器分配，只增不减；`box_key` 为 0 表示尚未分配。矿车实体上的 `box_key` 计分标识归属。
- **无投掷者的触发物被忽略**：发射器、狐狸等丢出的命名绿宝石没有 `Thrower`，读取编号得到 0，源码直接跳过，不会建立共享的 0 号箱子。
- **掉落物只有一次触发**：掉落物被标记 `pc_processed`，同一枚掉落物不会每刻重复切换。
- **物品安全**：收起流程使用 `自身.保存并移除`：先把矿车 `Items` 追加进绿宝石的寄存区，确认写入成功后才清空矿车并移除实体，因此不会把箱内物品掉在地上；写入失败时矿车保持原样，可以再次触发重试。绿宝石丢失、烧毁或删除时寄存物品也会随之丢失；管理员直接删除实体、清除计分板或清空物品组件属于外部状态修改，不在切换协议内。
- **一名玩家同时使用多枚钥匙**：编号与开关状态按玩家共享，而寄存区跟随被丢出的那枚绿宝石。多枚钥匙交替触发时物品不会被覆盖（追加语义），但同一玩家同时只应放出期望数量的箱子。
- **未加载区块中的矿车**：实体选择器只能看到已加载区块里的矿车。若玩家把矿车留在远处再触发收起，本次收起不会生效（状态回到未放出）；再次触发会召唤新箱子，旧矿车仍在原处，靠近后仍可打开。
- 矿车可以在主世界、下界和末地之间收取；当前实现不扫描数据包添加的自定义维度。

## 手工验收

- 两名玩家各自触发：触发后各自只有一辆属于自己的 `pc_box` 矿车，编号计分不同。
- 玩家 A 收起箱子时，玩家 B 的箱子不受影响。
- 首次触发后只有一辆带 `pc_box` 标签的箱子矿车，触发用的绿宝石立即回到投掷者背包且名称与组件不变。
- 反复投掷同一枚绿宝石可以持续切换；不会消耗或复制绿宝石。
- 背包已满时触发，绿宝石留在投掷者附近的地面而不是消失。
- 箱内物品包含不同槽位、堆叠数、耐久和组件时，收起后地面没有掉落物（矿车在清空后才被移除），绿宝石的 `minecraft:custom_data.pc_items` 里能看到完整列表。
- 箱内的矿车即使被岩浆/爆炸波及也不会被摧毁（无敌），停留在召唤位置不会下落或滑动（无视重力）。
- 再次放出后，物品的槽位、数量和组件保持不变。
- 连续执行 `/reload` 后，已放出的矿车、已收起的寄存物品和每位玩家的编号都不会被重置。
- 用发射器丢出命名绿宝石不会建立箱子。
- 普通绿宝石、名称 `a`、名称 `AA` 和两个一组的 `A` 绿宝石不会触发。
